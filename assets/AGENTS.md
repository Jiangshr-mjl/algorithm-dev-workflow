# AI 算法开发协作规则

本文件约束在本项目内工作的 AI。目标是让用户始终知道：这次改了什么、为什么这样写、从哪里继续。

## 接手项目

- 先阅读 `DEV_STATE.md`，再阅读其中引用的尝试记录和相关代码。
- 简短说明当前目标、代码状态、已确定的结论和下一步；不要因为接手就自动修改或运行。
- 记录与实际文件不一致时，先指出差异，不把旧结论当作当前事实。
- 不运行记录里保存的命令，除非用户明确授权本次运行。

## 每次围绕一个目的

用户要求修改时，修改前简短说明：目的、预计改动范围、验证方式。一次尝试可以涉及多个文件，但必须围绕同一个目的。

- 新尝试使用 `EXP-0001`、`EXP-0002` 等连续编号；检查现有记录，使用下一个未占用编号。
- 从 `experiments/TEMPLATE.md` 复制结构创建 `experiments/EXP-编号.md`，填写实际信息；不为纯解释创建尝试。
- 同一目的下的审查修订沿用原编号，追加修订摘要；新目的使用新编号。
- 额外优化先记为后续事项，不顺手重构、改名或整理无关内容。
- 默认完成当前尝试、讨论结果后，再按用户选择进入下一次尝试，不自动开展多轮优化。

## 修改前保证可恢复

- 先检查工作区现状，保留用户已有改动，不覆盖、不重置。
- 有有效 Git 仓库时，记录基线提交和工作区是否有未提交改动；提交号不能代表未提交内容。对将被修改且存在未提交改动或未跟踪的文件，额外保存修改前副本。
- 无有效 Git 仓库时，把将被修改的已有文件备份到 `experiments/baselines/EXP-编号/`，保留相对路径并在记录中列明。
- 同一尝试第一次修改某文件前保留基线；后续审查修订不覆盖这份基线。新增文件注明“新增，无旧版本”。
- 不为落实本规则自动初始化仓库、提交或安装工具。

## 简单调整直接完成

- 用户明确要求的绘图布局、配色、字体、标签、图例、输出格式等简单调整，以及不改变计算含义的局部修正，修改后直接运行同范围必要验证，无需再次询问。
- 简单调整不得改变科学算法、数据筛选/插值/积分口径、统计样本或指标定义，不扩大处理范围或外部写入权限，不覆盖需保留的历史结果。按实际影响判断，不按改动行数判断。
- 简述改动范围、保留必要基线、沿用同一尝试编号并记录新输出与验证结果；无需强制停在待审查。
- 同范围的布局/文字验证问题可直接修正并重验；涉及算法/数据变化、原因不明、权限不足，或同一问题连续两次修正仍失败时，记录并停止，说明原因及下一步。
- 用户当前明确偏好和授权优先于旧版流程；用户要求先审查或禁止运行时遵从。不得因代码文件变动本身重复索取许可。

## 实质变化先审查，再运行

本节适用于算法、数据处理口径、统计定义或运行范围的实质变化；上述简单调整直接完成并验证。

修改完成后提供简明改动说明：

| 内容 | 说明要求 |
| --- | --- |
| 改动概览 | 哪些文件变化，各自承担什么作用 |
| 核心逻辑 | 原来如何处理，现在如何处理，修改理由 |
| 阅读入口 | 先看哪一段，再看哪里；提供准确文件位置 |
| 待验证点 | 哪些行为或效果尚未验证，建议怎样验证 |

实质变化随后停在“待审查”；简单调整可直接进入“运行中”。

- **提问默认只要求解释。** “为什么这样写”“这里是不是有问题”等疑问不授权修改或运行；解释期间保持所有文件稳定，包括状态和记录。
- 用户明确要求修改时才修改。实质变化后讲清新增变化，重新进入“待审查”；简单调整直接验证。
- 用户认可代码但没有同意运行时，标记“待运行”，继续等待。
- 只有用户明确同意运行后，才执行获准范围内的实验、测试、构建、基准或其他验证命令。用户的明确指令可以一次授权若干项已说明的验证。
- 许可针对用户已审查的代码和运行范围；算法/数据口径等实质变化或运行范围扩大后，重新审查并取得相应运行许可。简单调整按上节直接验证。
- 实质变化运行失败时先记录实际情况、说明原因或未知原因、提出修复建议，不自动改代码重跑。简单调整仅按上节允许的范围修正和验证。
- 读取文件、查看差异和 Git 状态可用于理解现状；它们不代表实验验证。不得用导入代码、启动程序等方式绕过运行许可。
- 自然语言表达即可，不要求用户使用固定口令。仅“继续”而没有明确对象时，不将其推定为运行许可。

## 记录与阶段结论

AI 负责维护记录。修改完成、用户作出审查决定、运行结束、阶段结论确定时，更新尝试记录和 `DEV_STATE.md`。纯解释不改文件。

- `DEV_STATE.md` 只保留当前目标、采用的代码状态、当前编号和阶段、最近确定的结论、未决问题及下一步，并链接相关记录。
- 尝试记录保存：目的、基线、改动摘要、审查决定、实际运行方式、结果位置和结论；不抄录每一条工具操作或整段对话。
- 没有运行的改动必须写“未验证”；建议命令与实际执行命令分开，未执行的字段写“未运行”。
- 实际运行需保留工作目录、命令、关键参数、数据或输入版本、指标和必要环境信息；未知信息写明未知，不编造。
- 运行失败、无提升和中断也保留简短结论。比较效果时记录基线、指标、运行条件；条件不同则说明局限。
- 区分事实、推测与待验证点。运行成功不等于效果提升；用户未决定时，不宣称已采用该改动。
- 结果出来后，给出保留、撤回或继续验证的建议，记录用户的决定；撤回实际文件修改也需用户明确要求。

阶段取值：`待审查` → `待运行` → `运行中` → `待讨论结果` → `已结束`。用户同意运行或要求简单调整时可直接进入运行中。实质性修订回到待审查；简单调整直接验证。失败或中断记录实际情况。结束时注明保留、撤回或暂存待验证。

## 文件组织与恢复掌握

- 在正式源码上修改，不生成 `final2`、`new_new` 等并列版本。
- 实验输出默认放在 `experiments/outputs/EXP-编号/`；多次运行用 `run-001` 等子目录，避免覆盖已有结果。项目已有合适输出约定时沿用，并记录实际位置。
- 临时脚本明确用途和所属尝试编号，与正式源码分开；只在需要时创建目录和脚本。
- 清理前列出文件用途与保留建议，用户确认具体删除范围后再删除。
- 用户说“现在太乱了”时，暂停新增修改和实验，先只读梳理已确定内容、未确定内容、当前文件状态及可选下一步。用户选择后再继续。

## 使用与试用

- 新对话可说：“先阅读项目的当前状态和相关尝试记录，向我解释现在做到哪里，暂时不要修改或运行。”
- 将规则用于其他项目时，合并到该项目已有的 `AGENTS.md`，不要覆盖原有约定；创建符合实际情况的状态文件并带上尝试模板。
- 先完成两次真实尝试，再评估是否需要调整记录粒度。验收项目见 `DEV_STATE.md`。
